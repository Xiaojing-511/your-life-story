# 分享链接「完整复原」方案（含图片/视频/BGM）

> 目标：分享出去的链接，接收方打开后看到的和作者本地效果**完全一致**——
> 同样的路、同样顺序的回忆、同样的文字、照片、视频（以及可选的故事专属 BGM），且全程只读、无法编辑。
> 部署不再用 GitHub Pages，改用**腾讯云 CloudBase**（免备案、带默认 HTTPS 域名，后续可换自有域名显得更专业）。

> **实施状态（2025-09）：** 前端代码已全部落地 —— v2 云快照上传/拉取/撤回、
> 只读体验模式接入、BGM 还原、体积限制、本地 mock、E2E 脚本
> （`scripts/verify-share-cloud.mjs`，本地 12/12 通过）。
> ⏳ **剩下的是控制台一次性配置（5 步，见 `cloud/README.md`）**，配好后即可真机验证。

---

## 0. 结论（为什么必须这样设计）

现状（代码确认过）：

- 照片/视频 Blob 存在本机 **IndexedDB**（`mls-assets`），文字世界存在 localStorage；
- 本地显示靠 `URL.createObjectURL`，只有作者这台机器能看见；
- 现有分享（`js/share.js`）只把文字压进 URL，**故意丢掉照片/视频**；
- 接收端渲染层 `ui.js` 只认 `mem.image`(URL 字符串) 和 `mem.video`({url, poster})——**不依赖本地对象 URL**。

所以让接收方看到图片/视频，唯一办法是：**分享时把二进制上传到一处公网可读的云存储，URL 里只带一个短 ID；接收方打开链接后按 ID 拉取故事包（含媒体 URL），走现有只读模式渲染。**

结论选型（按你的回答）：

| 决策点 | 你的选择 | 方案落点 |
|---|---|---|
| 基础设施 | 有云账号、没买服务器 | 用 CloudBase「静态托管 + 云存储 + 云函数」，**不需要买服务器** |
| 媒体策略 | 必须完全复原；可在本地配置限制体积 | 原样上传（不转码），本地分享前用配置限制单文件/总量上限 |
| 分享形态 | 快照式 + 可随时撤回 | 每次分享生成独立快照目录；撤回 = 删目录 |
| 有效期 | 永久 | 永久有效，手动撤回 |
| 区域 | 免备案优先 | CloudBase 默认域名（HTTPS、免备案），后续可绑自定义域名 |

## 1. 架构

```
作者浏览器                         腾讯云 CloudBase（一个环境，无需服务器）
─────────────                      ─────────────────────────────
「我的游戏 → 分享」
  1. 打包 story.json(文字+布局+媒体清单)
  2. 生成 shareId(随机 14 位) ── 上传到云存储 ──▶ 静态托管: 游戏本体(index.html/js/css)
  3. 逐文件上传 照片/视频/BGM      云存储: shares/<shareId>/
     (SDK 直传，支持断点/进度)              ├── story.json      (文字+布局+清单)
  4. 调云函数 finalizeShare 校验     │          （媒体清单: media/<memId>.png 等）
     并标记「已发布」                 ├── media/*           (图片/视频原文件)
                                        └── bgm.*            (可选，故事专属 BGM)

接收方浏览器
  打开 https://<name>-<envId>.webapps.tcloudbase.com/#share=s3.<shareId>
  → 前端发现 s3. 前缀 → fetch 云存储 shares/<shareId>/story.json
  → 把媒体清单拼成绝对 URL → 构造 memories(image: URL / video:{url,poster})
  → 进入现有「只读体验模式」(game.js) —— 渲染层 ui.js 零改动

撤回: 作者点「撤回」→ 云函数删除 shares/<shareId>/** → 链接变 404，即失效
```

- **静态托管**：放游戏本体，替换 GitHub Pages（也是以后分享链接的基底地址）。
- **云存储**：只放 `shares/<shareId>/` 快照目录；公开读、匿名写仅限该随机目录（防猜靠随机 ID + finalize 校验），个人规模够用。
- **云函数**：只做两件小事——`createShare`（发 ID/校验 manifest）和 `revokeShare`（删除目录）；媒体文件走 SDK **直传**（绕开云函数 6MB 请求体限制，15MB 视频没问题）。
- 成本量级（个人使用：几十到几百 MB 存量、每月几 GB 下载）：通常落在免费额度内，超了也就几块钱/月。

## 2. 链接与数据协议（v2，向后兼容）

### 链接格式

```
https://<name>-<envId>.webapps.tcloudbase.com/#share=s3.<shareId>
                       旧链接(纯文本) #share=<base64…> 仍可打开 —— decode 时区分前缀
```

> 链接形态：分享出的链接同时带 `?share=s3.<id>` 与 `#share=s3.<id>`
> （query 里的那份用于 CloudBase 默认域名「风险提醒」中间页跳转后 hash 丢失的恢复；
> 纯文字版因含隐私内容只放 hash）。解析顺序 hash 优先、query 兜底。

`share=` 负载现在分两类：

- 以 `s3.` 开头 → **云快照**：取 `<shareId>` → `GET <存储域名>/shares/<shareId>/story.json`
- 否则 → **旧版纯文本**：走现有 `ShareCode.decode`（兼容已发出去的链接）

### story.json（快照清单）

```jsonc
{
  "v": 2,
  "shareId": "ab12cd34ef56gh",
  "createdAt": 1760000000000,
  "title": "……", "name": "", "origin": "manual",
  "gender": "female",
  "worldLength": 4800,          // 快照当时的布局，保证路完全一致
  "memories": [
    {
      "id": "m1", "title": "……", "emoji": "🌻", "color": "#e07b8a",
      "text": ["……"],
      "x": 400,                  // 回忆位置
      "media": {
        "image": { "file": "media/m1.png", "mime": "image/png" },   // 有照片才有
        "video": { "file": "media/m1.mp4", "mime": "video/mp4" }     // 有视频才有
      }
    }
  ],
  "bgm": { "file": "bgm.m4a", "mime": "audio/mp4" } | null   // 故事专属 BGM，可选
}
```

接收端把 `media.file` 拼上快照 `base`（= 文件所在目录 URL）即得可直接渲染的 memories：

```js
mem.image = <base>/media/m1.png
mem.video = { url: <base>/media/m1.mp4, poster: mem.image || undefined }
// 与 store.loadActiveWorld() 产出的结构一致 → ui.js 无需改动
```

> 注意：`x`/`worldLength` 必须随快照固定（分享那一刻的排布），而不是接收端重排，
> 这样「初始看到的画面位置」也和作者一致——正好对应现有 `game.js` 里
> `hasLayout ? 用快照布局 : 重新排布` 的分支。

## 4. 体积限制（在本地配置，简化实现）

在 `js/site-config.js` 加一组「分享版」上限，上传前在本地先拦（不必等服务端）：

```js
shareLimits: {
  imageMB: 1,      // 单张照片 ≤1MB（创作时已压到 1280px，通常几十~几百 KB）
  videoMB: 15,     // 单视频 ≤15MB（沿用创作时的上限）
  bgmMB: 20,       // BGM ≤20MB（沿用）
  totalMB: 80,     // 一次分享总上限（≈5 段回忆各带 15MB 视频 + 1 个 BGM）
},
```

- 上传前逐项检查，超了直接提示是哪一段哪个文件超限，让作者在编辑页删/换；
- 上传中断支持重试（SDK 断点续传能力）；
- 总包预计几十 MB：分享时明确提示「含 x 张照片 / y 段视频，共约 z MB，建议在 Wi-Fi 下分享」。

## 5. 云端开通与部署步骤（一次性，约 20 分钟）

1. 腾讯云控制台开通 **CloudBase 云开发**，新建环境（选带静态托管 + 云存储 + 云函数，任意地域均可，**中国地域默认域名免备案**；若后续绑自定义域名需备案）；
2. 环境 → 静态托管：上传 `index.html` + `css/` + `js/`（内置 `assets/` 如有）→ 得到 `https://<name>-<envId>.webapps.tcloudbase.com`（HTTPS）；
3. 云函数：新建 `createShare` / `revokeShare`（Node，代码放在仓库 `cloud/functions/` 下，用 `@cloudbase/cli` 或控制台上传）；
4. 云存储安全规则（简版）：

   ```jsonc
   // 读：任何人（接收方免登录直接看）
   // 写：任何登录态(含匿名)可写，但仅限 shares/ 下的随机目录 —— 防猜靠 128bit 随机 ID
   { "read": true, "write": "auth != null && resource.path.startsWith('shares/')" }
   ```

5. Web SDK 初始化：`@cloudbase/js-sdk` + **匿名登录**（`auth.signInAnonymously()`），只用于上传；
6. 把环境变量填进 `js/site-config.js` 的 `cloud` 字段；
7. 部署前本地用 mock 跑通（见里程碑 1），再切真实环境验证端到端。

> 想要「更专业」的域名：之后买一个域名 → 备案 → CloudBase 静态托管绑定自定义域名
> （备案只需域名，无需服务器，费用仅域名费），`SITE_CONFIG.shareBase` 一改即可，代码零改动。

- **里程碑 0（半天）**：CloudBase 部署静态站 + `SITE_CONFIG.shareBase` 指向新域名；验收：打开新域名和本地效果一致。
- **里程碑 1（1~2 天，不依赖云）**：`share-cloud.js` + `share.js` v2 + 分享面板 + mock 服务（`scripts/mock-share-server.mjs`，本地 8090 端口）。验收：本地分享一个**带照片和视频**的故事 → 用另一个浏览器(无 IndexedDB 数据)打开链接 → 走完全程，照片/视频可见；`scripts/verify-*.mjs` 全绿。
- **里程碑 2（1~2 天，接真实云）**：建环境/函数/规则；上传走 CloudBase SDK；真机（手机微信/浏览器）验证；旧纯文本链接仍能打开。
- **里程碑 3（可选加固/体验）**：「我的分享」列表（本机记录 shareId，管理撤回）、撤回后 404 验证、CDN 缓存头、自定义域名、量级大了再加服务端限流/内容审核。

## 7. 风险与对策

| 风险 | 对策 |
|---|---|
| 存储公开可写 → 被塞垃圾 | 随机 ID 不可枚举 + `finalizeShare` 校验 manifest 与体积；个人量级足够，超了再加匿名频控 |
| 撤回后 CDN 缓存仍可访问 | 文件 URL 带随机目录本身不会被缓存到公共 CDN 默认关闭；确认 CloudBase 存储读缓存策略，必要时在 story.json 里带版本号 |
| 15MB 视频直传绕云函数体积限制 | 媒体走 SDK 直传（非云函数转发），已考虑 |
| 旧链接失效/降级 | 前缀分发：`s3.` 走云端，其余走旧解码，平滑过渡 |
| 上传中断 | SDK 断点续传 + UI 重试 |
| 内容敏感（人生故事+本人照片） | 链接即密钥：不回帖公开传播；提供撤回；以后可加「访问需作者批准」等 |
| 未备案默认域名观感 | 域名短、https 正常，够用；正式对外前绑自定义域名即可 |
